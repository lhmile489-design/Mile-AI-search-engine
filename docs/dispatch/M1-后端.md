### 交付 1：`backend/docs/接口设计-草案.md`

按全局规范的对接文档最小结构写（方法、路径、功能、鉴权、请求体、响应、字段说明、错误码），覆盖 PRD §8.2 的 6 个接口。以下约定已经定了，直接写进去：

| 项 | 约定 |
| --- | --- |
| 普通接口响应体 | `{ code, msg, data }`，成功码 `200`（整数） |
| 时间 | ISO 8601 字符串，带时区；耗时为毫秒整数 |
| 分页 | 入参 `page`（从 1 开始）/ `pageSize`；出参 `total` / `records` |
| 字段命名 | 接口 JSON 用 camelCase，数据库用 snake_case |
| SSE 心跳 | 整个流期间每 10 秒发一次注释行 `: ping\n\n`（M0 前端实测：Next 代理 30 秒无数据会断开） |
| SSE 帧 | `event: <名>\ndata: <单行 JSON>\n\n`；每条事件带递增 `id` |
| SSE 错误 | 流内出错发 `error` 事件后关闭，不发 `done`；请求校验失败在建立流之前直接返回 400 + 统一响应体 |

需要你设计并写清楚的：

1. **SSE 六类事件的完整载荷**（`trace` / `sources` / `token` / `related` / `done` / `error`），每类给字段表和一个 JSON 示例。示例里的信源字段值取自 `docs/probes/*.json` 的真实数据，不要编。
2. **`SourceCard` 统一结构**：把 Tavily 和 DeepSeek 两家的字段映射到一套内部字段，给一张映射表（原字段 → 内部字段 → 处理规则）。必须覆盖：
   - URL 归一化：去掉 `#` 片段后再去重，规则写清楚
   - 发布时间：RFC 1123 和 RFC 3339 统一成 `publishedAt`；拿不到就是 `null`
   - 原文片段：`raw_content` / `content` 的清洗规则（M0 发现的 `2000 character limit reached` 前缀、导航文本）和长度上限
   - 信源 `id`：两家返回的 id 都不稳定，给出本项目自己的稳定 id 生成规则
3. **重排分数口径**：Tavily `score` 是 0–1 的纯相关性；DeepSeek `rerank_score` 是 0–3 且已经混合了权威性和时效性。给出方案，保证不重复计算，并写进对接文档。可选做法举例：DeepSeek 引擎下 relevance 用归一化后的 `rerank_score`，同时调低或关闭 authority、freshness 的权重。你也可以提别的方案，写明理由。缺失项按 PRD §6.3「权重按比例分给其他项」。
4. **范围过滤**：5 个类别与域名规则表（含 M0 发现的镜像域名 `alphaxiv.org`、`ar5iv.labs.arxiv.org`）；两家引擎第 2 层过滤分别怎么做（Tavily `exclude_domains`，DeepSeek 在 query 里拼 `-site:`，注意 128 字符上限怎么处理）。
5. **分类接口抽象**：`Classifier` 的输入输出。P0 实现本地域名规则；Jev 字段（`criteria`、`answers.<id>.choice`、`confidence`）按 B 级写，标「未确认」，留替换位。
6. **OpenUI 代码块约定**：研报 Markdown 里怎么标记 OpenUI 代码块（建议 ```` ```openui ```` 围栏）。语法用 OpenUI Lang 原生语法（`root = X(...)`、位置参数），**组件签名由前端在本轮出草案**，你这里只写围栏约定和引用，不要自己定义组件。
7. **错误码表**：至少覆盖参数错误、上游超时、上游鉴权失败、上游额度用尽、上游限流、内部错误、客户端已中止（只写日志，不下发）。每个码写 `retryable` 是否为真。
8. **LLM 调用约定**：模型 `deepseek-flash`（A 级实测存在），`thinking: {"type": "disabled"}`，流式 `stream_options.include_usage=true`。写明 `tokenStats` 从哪个 chunk 取。
9. **缓存键与回放**：键的组成和归一化规则；回放时 `trace` 带 `cacheHit: true`，耗时是本次真实耗时。

### 交付 2：`backend/docs/数据库设计-草案.md`

1. 表清单。至少有 `search_history`（参照 PRD §7.1），按需加表，每张表说明理由。
2. 字段表：名称、类型、必填、默认值、说明；JSON 列写清楚内部结构，引用交付 1 的 `SourceCard`。
3. 索引：列表页按时间倒序分页要用到的索引。
4. 状态与枚举字段的全部取值，前后端共用。
5. **迁移方案**：SQLite 没有 Flyway，设计一套轻量方案：`app/db/migrations/V{n}__{描述}.sql` + `schema_version` 表，应用启动时按版本号顺序执行未执行过的脚本。写明幂等要求、失败处理、回滚方式（SQLite 的 `ALTER TABLE` 限制要考虑）。本阶段只写方案和 `V1__init.sql` 的 SQL 文本（放在文档里，不建文件）。
6. 存储什么、不存什么：中止和失败的检索不入库（PRD D6）；原文片段存多长。
