## 1. npm 包核实

### 1.1 `@openuidev/react-lang`：存在，可用，但教程的 DSL 写法不能直接用

| 项 | 结果 |
| --- | --- |
| 版本 | 1.1.0（`latest`），最后更新 2026-11-04 |
| 仓库 | `github.com/thesysdev/openui`，目录 `packages/react-lang`，MIT |
| 依赖 | `@openuidev/lang-core` ^1.1.0、`@openuidev/observability` ^0.0.4、`@openuidev/devtools` ^0.3.1 |
| peer | `react`（README 写 >=19.0.0）、`zod` ^3.25 或 ^4（当前 zod 最新 4.6.7） |
| 是否导出 `Renderer` | 是。同时导出 `createLibrary`、`defineComponent`、`createParser`、`createStreamingParser`、`generateSystemPrompt` 等（核对 `dist/index.d.mts`） |
| 解压体积 | react-lang 699 KB、lang-core 1.47 MB、devtools 879 KB（npm `dist.unpackedSize`，不是打包体积） |

**安装时会发遥测。** `lang-core` 带 `postinstall` 脚本（`dist/postinstall.mjs`），会向 PostHog 发 POST 请求，并在 `~/.config` 下写文件。脚本里的说明原文：发送加盐的项目 ID、OpenUI/Node/OS/包管理器信息，以及 PostHog 观察到的 IP；不发送仓库地址、路径、源码、提示词。关闭方式：环境变量 `OPENUI_TELEMETRY_DISABLED=1` 或 `DO_NOT_TRACK=1`。M3 安装时需要先设好其中一个，或用 `--ignore-scripts`。

**语法和教程不一致。** OpenUI Lang 的真实语法（来自 lang-core README 和内置提示词规则）：

- 每行一条语句：`标识符 = 表达式`。
- 必须有 `root = <根组件>(...)`，且建议放在第一行，流式时外壳先出现。
- 参数是**位置参数**，顺序等于组件 props 的定义顺序；子节点用名字引用，数组写 `[a, b]`，对象写 `{k: v}`。

教程写法是「缩进子行 + 命名参数」：

```text
HardwareBenchmarkCard(title="FlashAttention-3 vs FlashAttention-2 吞吐对比 [1]")
  column(key="kernel", label="内核架构", sortable=false)
  row(kernel="FlashAttention-2", precision="FP16", tflops="350", gain="基准 1.0x")
```

在临时目录装好 lang-core（`--ignore-scripts`，没进项目），用 `createParser` 实测：

| 输入 | 结果 |
| --- | --- |
| 教程原文 | `root: null`，`statementCount: 0`，什么都没解析出来，也不报错 |
| 原生语法但用命名参数 | 报 `type-mismatch`（`/rows` 期望 array 得到 string）、`excess-args` |
| 原生语法（见下） | 4 条语句全部解析，`errors: []`，得到完整元素树 |
| 原生语法，流式截断在半行 | `partial: true`、`incomplete: true`，未写完的 Column 报 `missing-required`，不抛异常 |

能解析的原生写法：

```text
root = HardwareBenchmarkCard("FA3 vs FA2 [1]", [c1, c2], [r1])
c1 = Column("kernel", "内核架构", false)
c2 = Column("tflops", "吞吐", true, true)
r1 = Row({kernel: "FlashAttention-2", tflops: "350"})
```

**结论与建议：用这个包，DSL 改用 OpenUI Lang 原生语法。**

- 好处：自带流式解析（`createStreamingParser`）、错误信息（`meta.errors`）和提示词生成（`library.prompt()`）。F11 的「解析失败降级为源码视图」可以直接用 `meta.errors` 非空或 `root === null` 判断。
- 代价：后端生成研报的 System Prompt 必须按原生语法写示例，**这是跨端契约**，需要主调度在 M1 定稿（见 `M0-问题记录.md` 第 Q3 条）。
- 不建议为了贴合教程写法而自写解析器：教程的缩进写法没有正式语法定义，自写要自己处理流式截断和容错。

### 1.3 代码高亮：选 `rehype-highlight`

| 候选 | 版本 | 解压体积 | 工作方式 |
| --- | --- | --- | --- |
| `rehype-highlight` | 7.0.2 | 26 KB（依赖 lowlight 3.3.0 60 KB、highlight.js 11.12.0 5.5 MB） | 同步 rehype 插件，输出 `hljs-*` 类名 |
| `shiki` | 4.6.0 | 602 KB（另有 langs、themes、引擎包） | 异步加载语法和主题，输出内联 `style="color:#..."` |

选 `rehype-highlight` 的理由：

1. **流式渲染**：研报每来一个 `token` 事件就重渲一次。`rehype-highlight` 是同步插件，直接挂在 `react-markdown` 的 `rehypePlugins` 上，每次渲染结果稳定。shiki 是异步高亮，每次增量都要等 Promise，中间态要么不高亮要么闪一下。
2. **令牌规则**：rehype-highlight 只输出类名，颜色可以在 CSS 里用 `--ink`、`--accent-deep` 等令牌定义。shiki 默认把主题色写成内联 hex，和「组件里不出现 hex」的规则冲突。
3. **体积**：highlight.js 解压体积大，是因为包含全部语言；lowlight 默认只用 `common` 约 37 种语言，打包时只进用到的部分。实际打包体积未测，M3 安装后用 `npm run build` 的输出核对。

## 2. SSE 经 Next.js rewrites 转发

### 2.1 做法

- 探针服务 `scripts/sse-probe-server.mjs`：只用 Node 内置 `http`，监听 `127.0.0.1:8001`，路径 `/api/probe/stream`。查询参数 `count`、`interval`、`delay`（首条前静默）、`heartbeat`（周期性发 `: ping` 注释行）。响应头带 `Cache-Control: no-cache, no-transform` 和 `X-Accel-Buffering: no`。
- 计时客户端 `scripts/sse-probe-client.mjs`：用 `fetch` 读流，记录每条事件相对请求发出的毫秒数，同时打印 `content-encoding`。用它代替 `curl.exe -N`，时间戳更准。
- dev：`BACKEND_ORIGIN=http://127.0.0.1:8001 next dev --port 3000`。
- prod：`BACKEND_ORIGIN=http://127.0.0.1:8001 next build`，再 `next start --port 3000`。
- 测完已停掉全部进程，3000 / 8001 已释放；`.next` 已用默认配置重新生成，destination 回到 `http://127.0.0.1:8000`。

### 2.2 结果

| 用例 | 直连 8001 | dev 经 3000 | prod 经 3000 |
| --- | --- | --- | --- |
| 10 条，间隔 300ms | 逐条到达，跨度 2774ms | 逐条到达，跨度 2744ms | 逐条到达，跨度 2805ms |
| 10 条，间隔 4s（总时长约 36s） | — | 全部到达，36095ms | 全部到达，36111ms |
| 首条前静默 35s，无心跳 | — | **30007ms 时上游被断开，客户端挂住不报错**，被外层超时杀掉 | **30005ms 时上游被断开，客户端挂住不报错** |
| 首条前静默 35s，每 10s 心跳 | — | 全部到达，首条 35061ms | 全部到达，首条 35055ms |

所有经 3000 的响应 `content-encoding=none`，生产环境默认 `compress: true` 没有压缩 `text/event-stream`。

### 2.3 结论

1. **没有缓冲。** dev 和 prod 下事件都逐条到达，间隔和直连一致。PRD §13「rewrites 转发 SSE 时缓冲」这条风险可以关闭。
2. **有 30 秒空闲超时。** Next 内部代理默认 `proxyTimeout` 30000ms（`node_modules/next/dist/server/lib/router-utils/proxy-request.js` 第 37 行）。它是空闲超时：总时长超过 30s 但持续有数据没问题；连续 30s 没有数据，上游连接被断开。
3. **断开后浏览器侧收不到错误。** 客户端拿到了 200 和响应头，之后既没有数据也没有结束，一直挂着。前端如果只靠 `onerror` 或流结束判断，会永远停在 `retrieving`。
4. **`BACKEND_ORIGIN` 在构建时固定。** 用 `BACKEND_ORIGIN=...8001` 构建后，`.next/routes-manifest.json` 里 destination 就是 8001；只在 `next start` 时设置不生效。

### 2.4 建议方案

| 方案 | 说明 | 状态 |
| --- | --- | --- |
| A. 后端发心跳（推荐，写进契约） | 后端在整个流期间每 10–15s 发一行 SSE 注释 `: ping\n\n`。浏览器 `EventSource` 和 fetch 解析都会忽略注释行 | 已实测有效 |
| B. 前端空闲看门狗（推荐，和 A 一起做） | 前端 SSE 解析器记录最后一次收到字节的时间，超过阈值（如 45s）就主动 abort，进入 F08 超时错误态 | M3 实现 |
| C. 调大 `experimental.proxyTimeout` | `next.config.ts` 里设置；属于 experimental 配置 | 未实测 |
| D. Route Handler 自己转发 | 用 `app/api/[...path]/route.ts` 拿 fetch 流原样返回，绕开内部代理 | 未实测，只在 A 不可行时考虑 |

## 3. M3 新增依赖（2026-11-08）

安装前设置了 `OPENUI_TELEMETRY_DISABLED=1`（决策 Q6）。本轮不装任何 OpenUI 包（M5）。证据等级：A = 本机 `npm install` 成功并在测试或构建中实际运行过。

| 包 | 安装版本 | 用途 | 证据 |
| --- | --- | --- | --- |
| `react-markdown` | 10.1.0 | 研报 Markdown 渲染，peer `react >=18` | A：`npm ls` 已安装；`src/lib/__tests__/citations.test.tsx` 用 `renderToStaticMarkup` 实际渲染通过；`next build` 通过 |
| `remark-gfm` | 4.0.1 | 表格、任务列表、删除线 | A：同上，已挂在 `remarkPlugins` |
| `remark-math` | 6.0.0 | 解析 `$...$` 公式 | A：同上 |
| `rehype-katex` | 7.0.1 | 渲染公式；`throwOnError:false`，错误色继承文字色 | A：同上 |
| `katex` | 0.16.47（`^0.16.47`） | 公式样式表 `katex/dist/katex.min.css`。按决策 Q7 锁 0.16 线，不装 0.19 | A：`npm ls katex` = 0.16.47；`npm view katex versions` 确认 0.16.47 是 0.16 线最新 |
| `rehype-highlight` | 7.0.2 | 代码块高亮，同步插件，适合流式整体重渲染（理由见 §1.3）。配置 `detect:false, ignoreMissing:true`，`openui-lang` 等未知语言按普通代码块显示。颜色在 `globals.css` 用令牌定义，不引入第三方主题 CSS | A：同上 |
| `vitest`（dev） | 4.1.12 | 单元测试，node 环境，不需要 jsdom | A：`npm test` 62 项通过 |

选型与安装中遇到的问题：

1. **vitest 选 4.x 而不是 latest（5.1.0）。** `vitest@5.1.0` 的 `@types/node` peer 要求 `^22 || >=24`，而项目 `@types/node` 是 `^20`（Next 脚手架），`npm install` 报 ERESOLVE。`vitest@4.1.12` 的 peer 是 `^20 || ^22 || >=24`，兼容。本机 npm 源（npmmirror）下直接 `npm install -D vitest@4.1.12` 还会触发 npm 10.9.9 的 arborist 异常 `Cannot read properties of null (reading 'edgesOut')`，加 `--legacy-peer-deps` 后安装成功。装完 `npm ls` 无冲突，`package-lock.json` 已更新。
2. **vitest 配置文件。** 包里没有 `"type": "module"` 时，`vitest.config.ts` 会触发 ESM 加载警告，所以配置文件用 `vitest.config.mts`；本机 vitest 4.1.12 带的 Vite 用 oxc 编译，JSX 运行时要写在 `oxc.jsx.runtime`，写 `esbuild.jsx` 会被忽略并打印警告。
3. **没有装 `motion`。** M3 的动效只有抽屉滑出、信源行入场，都是 CSS 的 `transform` / `opacity`，不需要动画库。§1.4 的结论保留给 M5。
4. **没有装 `@types/mdast` 和 `unified`。** 它们是 `react-markdown` 的传递依赖，已被提升到顶层 `node_modules`，`src/lib/citations.ts` 只做 `import type`。如果将来换包管理器导致不再提升，需要显式声明。
5. **Markdown 体积。** `/` 路由 First Load JS 121 kB；Markdown 链路（含 katex、highlight.js）在 `next/dynamic` 的独立 chunk 里：`.next/app-build-manifest.json` 的 `/page` 首屏 chunk 列表不含它们，实测含 `hljs`/`katex`/`micromark` 的 chunk 是 336 KB 与 257 KB（未压缩），均为懒加载。
